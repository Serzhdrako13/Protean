# OpenVPN & IKEv2 — design notes (in progress)

Status: building OpenVPN first, then IKEv2. This file records the decisions so
the implementation stays consistent.

## Certificates: internal CA + bring-your-own (BYOC)

Both VPNs are certificate-based. The panel abstracts cert provisioning behind
a `CertAuthority` interface (`internal/vpn/pki`), so the same code issues certs
regardless of where the CA comes from:

- **Internal CA** (default, zero host state): the panel generates a CA keypair
  with Go `crypto/x509`, stores it AES-encrypted in Postgres (same scheme as
  peer private keys), and issues server/client certs itself. No easy-rsa, no
  PKI files scattered on the host — only the issued server cert/key are placed
  on the host for the daemon.
- **BYOC / external CA**: the panel is given an existing CA cert **and key**
  (e.g. an intermediate exported from step-ca) and issues client/server certs
  under it with the same x509 code.
- **Future — step-ca ACME/API**: when step-ca is up and you'd rather not export
  its key, add a `stepca` CertAuthority impl that requests certs from step-ca's
  API/ACME instead of signing locally. The interface is already shaped for
  this; the panel would hold no CA private key at all. **TODO when step-ca
  lands.**

Rationale: doing the CA in Go keeps the panel dependency-light and host-clean,
and makes swapping to step-ca a matter of adding one interface implementation.

## Mesh membership is optional, per provider

Cross-provider no-NAT mesh is becoming an explicit **per-provider toggle**
(stored in DB), applied to every provider — wireguard, amneziawg, openvpn,
ikev2. A provider "in the mesh" contributes its tunnel CIDR to everyone's
routes and gets the FORWARD rules; a provider "standalone" is just an
independent access method. Defaults: wg/awg in-mesh (current behavior),
openvpn/ikev2 opt-in.

For a provider to join the mesh it must expose a tunnel CIDR and support the
forwarding rules — OpenVPN (server subnet + iptables) and IKEv2 (pool +
iptables) both can, so mesh membership is available to all four.

## Per-provider settings (implemented)

Each provider has independent settings (`protean.provider_settings`), edited on
the provider's **Network** page:

- **mesh_enabled** (default off) — join the cross-provider no-NAT mesh. Off =
  standalone parallel tunnel. Toggling only affects generated client configs
  (no host change).
- **internet_egress** (default off) — route clients to the internet through
  this VPN: hub adds a MASQUERADE rule (out the auto-detected default-route
  interface) and clients get a `0.0.0.0/0` route. Toggling restarts the
  interface.
- **service control** — start/stop/enable/disable the systemd unit (via the
  root-owned installer's `service` verb) to free resources on unused VPNs.

FORWARD rules are always on for a running wg-family interface (it needs to
route); egress adds NAT on top. Both live as panel-managed PostUp/PostDown
lines tagged `protean-fwd` / `protean-nat`.

## NOTE — multiple instances of one VPN (multisite), revisit later

The operator may want 2–3 separate wg (or other) configs on the same host
(e.g. multiple interfaces for a multisite setup, some in-mesh, some egress,
some standalone). The current model is one interface per provider. Multiple
instances per provider = a larger change (interface list per provider, chosen
in the UI) tied to the multi-server work. **Left for later; the per-provider
settings above already make each existing VPN independently configurable.**

## Topologies (decided) — see docs/TOPOLOGIES.md

Two supported topologies, chosen per provider: (A) panel-managed cross-provider
mesh (mesh toggle on) and (B) router-side merge / parallel tunnels (mesh off,
default — merge site networks on the routers). Both are first-class; mesh stays
optional per provider. No further mesh investment needed for the router-side
path — it works today via standalone mode. Full write-up in
`docs/TOPOLOGIES.md`.

## Per-provider specifics

### OpenVPN (implemented)
- Server config `/etc/openvpn/server/<iface>.conf`, unit `openvpn-server@<iface>`.
- Panel is its own CA (internal x509, key AES-encrypted in DB); server cert +
  tls-crypt key generated by the panel. `EnsureServer` writes ca/cert/key/
  tls-crypt/conf and enables the service ("Set up OpenVPN server" button).
- Client bundle: single `.ovpn` with inlined `<ca>/<cert>/<key>/<tls-crypt>`.
- Connected clients read from the status file (`status /run/.../status.log`).
- Site subnets per client via `client-config-dir` + `iroute`; tunnel IP via
  `ifconfig-push`.
- Host perms: setup-host.sh creates `/etc/openvpn/server` group-writable by the
  panel (server key lives there — same trade-off as the wg conf) and grants
  sudoers for `systemctl {enable,restart} openvpn-server@*`.
- **Mesh (implemented)**: cert providers can join the cross-provider mesh
  (Network page toggle). Routing plane: wg clients get routes to the cert
  provider's subnet (it's mesh-capable now), and the cert server pushes routes
  to the other mesh tunnels (via `EnsureServer` push-routes). Data plane: the
  cert provider's subnet gets a host FORWARD-accept rule via the root-owned
  installer's `forward add <cidr>` (interface-independent, since the tun/pool
  name isn't fixed; no NAT). Re-applied at startup (`ReapplyMeshForwarding`)
  because these rules, unlike wg-quick PostUp, don't survive a reboot.
- **Hot-apply (implemented)**: changing a cert provider's mesh OR egress toggle
  on the Network page re-provisions the server automatically (`provisionCert`
  -> EnsureServer with fresh push-routes/egress + mesh FORWARD). No manual
  "Set up server" needed.
- **BYOC CA import (implemented)**: the Certificate authority page
  (`/providers/{id}/ca`) accepts an external CA cert+key (e.g. step-ca
  intermediate); `ImportCA` validates via pki.LoadCA and stores it
  (source=external). Importing invalidates certs under the old CA -- re-provision
  and re-issue clients afterwards. (step-ca ACME, holding no key, remains a
  future CertAuthority impl.)
- **CRL/revocation (implemented)**: deleting a client revokes its cert. The
  serial is recorded (`revoked_certs`), the CRL is rebuilt from all revocations
  (`pki.CreateCRL`, monotonic `crl_number`) and written to
  `<server-dir>/crl.pem`; the server conf carries `crl-verify`. `EnsureServer`
  always writes a (possibly empty) CRL so the directive has a valid file.
  OpenVPN re-reads the CRL per new connection -- no restart. `NextUpdate` is set
  far out (CA horizon) because the file is rewritten on every change, so
  freshness is operational, not expiry-driven (an expired CRL would reject all
  clients). A currently-connected revoked client is blocked at its next
  (re)connection, not force-killed mid-session.
- **CSR-based enrollment (implemented)**: `AddPeerFromCSR` signs a
  client-supplied CSR (`pki.SignCSRWithCN`, CN forced to the panel-chosen name,
  client-auth EKU) so the private key never reaches the server. The stored
  client has a nil key; the `.ovpn` omits `<key>` and notes that the client
  pairs it with its own key file. Offered as an optional textarea on the Add
  client form.

### IKEv2 (strongSwan) — implemented
- swanctl config in `/etc/swanctl/conf.d/protean.conf`; certs under
  `x509`/`x509ca`/`private`; `EnsureServer` writes them and runs
  `swanctl --load-all` + enables `strongswan` ("Set up IKEv2 server").
- Panel is its own CA (shared `pki`, separate `ca_material` row "ikev2").
- Road-warrior model: clients get a pool address; server offers push-routes
  (site subnets + optional `0.0.0.0/0` for egress) as traffic selectors.
- Connected SAs parsed best-effort from `swanctl --list-sas` (wording varies
  by strongSwan version — keyed on "ESTABLISHED" + the remote identity).
- **Client export: PKCS#12 (.p12)** with a per-client random password (shown
  on the dashboard, 🔑) -- imports on iOS/macOS/Windows/Android/NetworkManager.
- Host perms: setup-host.sh makes `/etc/swanctl` group-writable by the panel;
  sudoers grants `swanctl` and `systemctl {enable,restart} strongswan*`.
- **CRL/revocation (implemented)**: deleting a client revokes its cert; the CRL
  is rebuilt (shared `pki.CreateCRL`, `crl_number` row "ikev2"), written to
  `x509crl/crl.pem` and `swanctl --load-all` reloads it so strongSwan's
  revocation plugin enforces it. `EnsureServer` mkdirs `x509crl` and writes a
  (possibly empty) CRL.
- **CSR-based enrollment (implemented)**: `AddPeerFromCSR` signs the client CSR
  (private key stays on the client). No `.p12` is possible without the key, so
  the export instead hands back the signed cert + CA chain (`<cn>-cert.pem`),
  which the client imports alongside its own key.
- **Per-client site subnets (implemented)**: a client with subnets (a site)
  gets a dedicated swanctl connection `<conn>-<cn>` matched on its cert CN
  (`remote.id`), advertising its LAN as `remote_ts` so the server routes to it;
  road-warrior clients stay on the shared connection (strongSwan prefers the
  more specific id-matched one). The connections file is regenerated + reloaded
  (`swanctl --load-all`) on every peer add/update/remove. The mesh push-routes
  (localTS) are persisted per server (`cert_server_routes`) so the provider can
  regenerate autonomously without the API recomputing them.
- **Single-file profiles (implemented)**: besides the default `.p12`, IKEv2
  offers `.mobileconfig` (Apple config profile: PKCS#12 payload + IKEv2 VPN
  payload) and `.sswan` (strongSwan Android app JSON, embedded p12). Exposed as
  extra download links on the dashboard and via `GET .../config?format=...`.
  Both embed the p12, so they need a server-held key (not available for
  CSR-enrolled clients -> those get a clear error). UUIDs are derived
  deterministically from the CN so re-downloads are idempotent on the device.
- **Limitations (backlog)**: list-sas parser is best-effort.
