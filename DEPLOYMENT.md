# Деплой и чеклист ручных шагов

Всё ниже — про один сценарий: панель и WireGuard/AmneziaWG крутятся на одной
и той же VPS, Postgres там уже работает в своём контейнере.

## 0. Единая сеть без NAT — что нужно на стороне площадок

Панель настраивает хаб (VPS) на форвардинг между всеми туннелями без NAT и
кладёт в клиентские конфиги маршруты на весь mesh. Но чтобы трафик реально
ходил в обе стороны до **устройств за клиентом** (LAN площадки, а не только
сам клиент), на стороне площадки нужно одно из:

- на LAN-роутере/шлюзе площадки добавить статический маршрут: «сети mesh
  (туннельные CIDR + чужие подсети) → через машину-клиента WireGuard»; **или**
- на самой машине-клиенте включить NAT/masquerade на её LAN-интерфейс
  (тогда remote-хосты видят трафик как исходящий от клиента и обратный
  маршрут не нужен); **или**
- если «клиент» — сам роутер площадки, включить на нём ip_forward.

Это вне зоны панели: панель управляет только хабом. Без обратного маршрута
будет пинговаться сам клиент, но не хосты в его LAN.

На хабе форвардинг включается на странице **Mesh** (кнопка «Enable» у
каждого транспорта — пишет PostUp/PostDown в конфиг и рестартит интерфейс).
Убедись, что подсети площадок не пересекаются (страница Mesh предупредит).

## 1. Скрипт `scripts/setup-host.sh`

Запускать на самом VPS, от root, интерактивно (не через `curl | bash` —
скрипт задаёт вопросы):

```
sudo ./scripts/setup-host.sh
```

Что делает, по шагам:

1. Определяет семейство дистрибутива (Arch / Debian-Ubuntu / RHEL-Fedora /
   openSUSE) по `/etc/os-release`. На **не-systemd** системах выходит с
   ошибкой (панель их не поддерживает).
2. Спрашивает, что ставить сейчас: WireGuard, AmneziaWG, OpenVPN, strongSwan.
   Это опционально — VPN можно поставить позже прямо из панели (страница
   Install).
3. **WireGuard/AmneziaWG**: ставит пакет, если конфига ещё нет — спрашивает
   адрес/порт, генерирует ключи, пишет `wg0.conf`/`awg0.conf`, включает и
   стартует `wg-quick@wg0`/`awg-quick@awg0`. Если конфиг уже есть — не трогает
   его, только читает порт для firewall-подсказки дальше.
4. **OpenVPN/strongSwan**: только ставит пакет. Панель их не настраивает и
   не управляет ими — это осознанно вне текущего функционала.
5. Всегда (даже если VPN сейчас не ставился — панель должна уметь поставить
   его позже):
   - создаёт системного пользователя `protean` (шелл — обычный `/bin/bash`,
     не `nologin`: SSH выполняет команды через шелл пользователя, с
     `nologin` панель вообще не смогла бы ничего запустить);
   - генерирует ему ed25519 SSH-ключ, публичный кладёт в
     `~protean/.ssh/authorized_keys`;
   - **кладёт root-owned installer** `/usr/local/lib/protean/protean-installer.sh`
     (0755 root:root — панель его менять не может);
   - ставит точечные `NOPASSWD` sudo-правила в `/etc/sudoers.d/protean`:
     путь installer-скрипта (аргументы whitelist-ятся внутри него),
     `wg`/`wg-quick`/`awg`/`awg-quick` и `systemctl restart
     wg-quick@*`/`awg-quick@*` — валидируется `visudo -cf` перед установкой;
   - выдаёт группе `protean-conf` (в неё входит `protean`) права на чтение
     и запись **именно на conf-файл(ы)** интерфейса(ов), плюс `+x` на саму
     директорию `/etc/wireguard`/`/etc/amnezia/amneziawg`, чтобы туда можно
     было зайти по пути.
6. Спрашивает про `net.ipv4.ip_forward=1` (нужно для маршрутизации между
   площадками через этот хост) — включает и сохраняет в
   `/etc/sysctl.d/99-protean.conf`.
7. Печатает подсказку по портам для файрвола — **не трогает файрвол сам**
   (риск отрезать себе SSH), только показывает готовые команды под
   ufw/firewalld, если они найдены.
8. Спрашивает про создание БД в уже работающем Postgres-контейнере: имя
   контейнера, admin-юзер, имя БД/роли (по умолчанию `protean`), пароль
   (можно принять сгенерированный). Создаёт роль и базу через `docker exec
   ... psql`, если их ещё нет.
9. Генерирует `.env` для панели (`SECRET_KEY`, `SESSION_SECRET`,
   `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `DATABASE_URL`, `PUBLIC_HOST` и т.д.)
   и SSH-ключ кладёт в `/root/protean-deploy/`.

Скрипт идемпотентен по большинству шагов (можно перезапускать — не
перезатирает существующие conf-файлы, ключи, роли/базы).

## 2. Что сделать руками после скрипта

- [ ] Скопировать `/root/protean-deploy/id_ed25519` → `./secrets/id_ed25519`
      (`chmod 600`) туда, где лежит `docker-compose.yml`.
- [ ] Скопировать `/root/protean-deploy/panel.env` → `./.env` там же.
- [ ] Открыть `docker-compose.yml`, у сети `postgres-net` выставить
      `name:`/использовать сеть, которую скрипт вывел в конце
      (`docker inspect <контейнер> ... .NetworkSettings.Networks`) —
      секция `postgres-net: external: true` должна указывать на реальную
      docker-сеть Postgres-контейнера.
- [ ] Прочитать `/etc/sudoers.d/protean` глазами — файл маленький, это
      единственное место, где у панели есть привилегии выше обычного юзера.
- [ ] Если на хосте `sshd_config` содержит `AllowUsers` — добавить туда
      `protean` (скрипт это только предупреждает, не правит sshd_config сам).
- [ ] Открыть в файрволе UDP-порты WireGuard/AmneziaWG (то, что скрипт
      подсказал) — сделать это самому, скрипт этого не делает.
- [ ] **Настроить reverse proxy с HTTPS перед панелью** (nginx/caddy) —
      см. ниже, это не опционально.
- [ ] `docker compose build && docker compose up -d`, проверить
      `docker compose logs panel` на чистый старт (миграции применяются
      сами при первом запуске).
- [ ] Зайти в UI, залогиниться `ADMIN_USERNAME`/`ADMIN_PASSWORD`,
      добавить тестового клиента, скачать конфиг, проверить `wg show` на
      хосте — что пир реально появился.
- [ ] Удалить `/root/protean-deploy` с хоста — секреты в нём уже не нужны
      после того, как ты забрал `id_ed25519`/`panel.env` себе в деплой.

## 3. HTTPS обязателен — иначе логин не сработает

Сессионная cookie панели выставляется с флагом `Secure`. Браузер **не
отправит** такую cookie обратно по обычному HTTP — значит, если открыть
панель как `http://ip:8080` напрямую (без TLS), после логина будет вечный
редирект обратно на `/login`. Панель рассчитана на то, что перед ней стоит
reverse proxy, терминирующий HTTPS; сама она отдаёт голый HTTP на
`127.0.0.1:8080`.

Пример для nginx:

```nginx
server {
    listen 443 ssl;
    server_name vpn.example.com;
    # ssl_certificate / ssl_certificate_key — свои

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

`X-Forwarded-For` панель использует только для rate-limit на login по IP —
не критично для работы, но полезно для честных логов.

## 4. Смена пароля админа

Штатно — через UI: страница **`/account`** (ссылка по имени пользователя в
навбаре), нужен текущий пароль. `ADMIN_USERNAME`/`ADMIN_PASSWORD` из `.env`
используются только для первичного засева, пока таблица `users` пустая.

Аварийный сброс (если пароль забыт): удалить пользователя и перезапустить
контейнер с новым `ADMIN_PASSWORD` — сидинг сработает снова:

```sql
DELETE FROM protean.users WHERE username = 'admin';
```

**2FA (TOTP)** включается на `/account` (по желанию, по умолчанию выкл):
кнопка Set up → скан QR в authenticator-приложении → подтверждение кодом.
После этого вход двухшаговый (пароль → код). Отключение — там же, требует
пароль. Если 2FA-устройство потеряно, снять флаг в БД:

```sql
UPDATE protean.users SET totp_enabled=false, totp_secret='' WHERE username='admin';
```

**Логи**: `LOG_LEVEL` (debug|info|warn|error) и `LOG_FORMAT` (text|json,
json удобно для сбора в Loki/ELK/Zabbix-log).

## 5d. Метрики (`/metrics`)

Prometheus-формат на `/metrics`, защищён Bearer-токеном `METRICS_TOKEN`
(пусто = эндпоинт выключен, 404). Один эндпоинт под оба сценария:

Метрики: `protean_up`, `protean_interface_up{provider}`,
`protean_peers_total/online{provider}`, `protean_rx/tx_bytes_total{provider}`,
`protean_listen_port{provider}`, и per-peer
`protean_peer_online/last_handshake_seconds/rx_bytes/tx_bytes{provider,peer}`.

**Zabbix (без Prometheus-сервера):** готовые шаблоны лежат в `zabbix/`
(`protean-zabbix-7.4.yaml`, `protean-zabbix-8.0.yaml`) — импортируй нужный,
слинкуй с хостом, задай макросы `{$PROTEAN_URL}`/`{$PROTEAN_TOKEN}`. Внутри:
master HTTP-item на `/metrics`, зависимые item'ы с preprocessing «Prometheus
pattern», LLD-дискавери пиров и триггеры (интерфейс down, пир offline, нет
метрик). Детали — `zabbix/README.md`. Вручную то же: HTTP-agent item + шаг
«Prometheus pattern» на метрику, напр. `protean_peers_online{provider="wireguard"}`.

**Prometheus/Grafana (если поднимешь позже):** в `prometheus.yml`
```yaml
scrape_configs:
  - job_name: protean
    authorization: { type: Bearer, credentials: "<METRICS_TOKEN>" }
    static_configs: [{ targets: ["<host>:8080"] }]
```
затем Grafana с источником Prometheus. Prometheus-сервер **не обязателен** —
без него метрики полностью покрываются Zabbix'ом выше. Альтернатива Grafana
без Prometheus — плагин Zabbix-datasource (Grafana читает прямо из Zabbix).

Эндпоинт не под сессионной авторизацией (скраперам неудобно), поэтому
`METRICS_TOKEN` — единственная защита: держи его секретным и по возможности
скрапь по loopback/внутренней сети, не наружу.

## 5. Бэкапы

Что нужно бэкапить, чтобы всё восстановить:

- **Postgres, схема `protean`**: сессии, справочник подсетей и *зашифрованные*
  приватные ключи клиентов, которые панель сгенерировала сама. Без этого
  бэкапа скачать конфиг уже созданного клиента повторно не получится —
  придётся пересоздавать клиента.
- **На хосте**: `/etc/wireguard/wg0.conf` и/или
  `/etc/amnezia/amneziawg/awg0.conf` — это полная конфигурация интерфейса
  и всех пиров. Это тот же файл, который правит и sudoers-скрипт, и
  панель — обычный бэкап хоста (или отдельный cron с копией) этого
  файла достаточно.
- **`SECRET_KEY` из `.env`** — без него зашифрованные приватные ключи в
  БД не расшифровать. Хранить отдельно от самой БД (например, в
  секретах CI/CD или password-менеджере), не только в `.env` на диске.

Перед каждой перезаписью конфига панель автоматически кладёт снапшот
предыдущего содержимого в таблицу `protean.conf_backups` (последние 20 на
интерфейс) — страховка от неудачной правки. Восстановить вручную:

```sql
SELECT saved_at, left(content, 60) FROM protean.conf_backups
  WHERE provider='wireguard' ORDER BY saved_at DESC;
-- скопировать нужный content обратно в /etc/wireguard/wg0.conf на хосте,
-- затем: systemctl restart wg-quick@wg0
```

## 5a. Усыновление существующих пиров

Пиры, заведённые вне панели (или до неё), видны на дашборде, но их
клиентский конфиг **не выгрузить** — приватного ключа у панели нет.
Кнопка **rotate** у пира генерирует новую пару ключей (имя, AllowedIPs и
keepalive сохраняются), после чего панель держит новый ключ и отдаёт
готовый `.conf`/QR. Старый ключ сразу перестаёт работать — надо
переустановить конфиг на клиенте. Это же — способ ротации при утечке ключа.

## 5b. Отключение пиров (disable/enable)

Кнопка **disable** у пира убирает его с живого интерфейса и из конфига, но
сохраняет его определение (pubkey, маршруты, keepalive, приватный ключ
остаётся в `peer_secrets`). Пир показывается на дашборде как «disabled» с
кнопкой **enable**, которая возвращает его как был. Так можно временно
отключить площадку без потери её ключей/настроек.

## 5c. Только один экземпляр панели

Панель берёт Postgres advisory-lock на старте и **откажется запускаться**,
если другой её экземпляр уже работает с той же БД (`another Protean
instance is already using this database`). Это намеренно: внутренняя
блокировка конфига и rate-limiter рассчитаны на один процесс. Не поднимай
2+ реплик на одну БД.

## 6. Осознанный компромисс: приватный ключ сервера в правах панели

Панель редактирует `wg0.conf`/`awg0.conf` напрямую (добавляет/убирает
`[Peer]`-блоки, правит `[Interface]`), поэтому SSH-пользователю `protean`
нужен доступ на чтение/запись к этому файлу — а в нём же лежит и
приватный ключ сервера (`PrivateKey =` в `[Interface]`). Панель никогда
не показывает и не сохраняет этот ключ в своей БД (он ей не нужен —
публичный ключ панель получает через `wg show ... dump`), но технически
компрометация панели или её SSH-ключа означает и компрометацию серверного
приватного ключа.

Альтернатива — не открывать сам файл, а дергать `sudo cat`/`sudo tee` на
конкретный путь и держать conf-файл 0600 root:root — тогда приватный ключ
сервера панели не виден вообще. Это более узкая модель прав, но сейчас не
реализована (текущий код читает/пишет файл без sudo). Если это критично
для модели угроз — сначала поменять `internal/sshexec` и провайдеров на
sudo-обёрнутый доступ к файлам, потом уже сужать sudoers/права на файл в
скрипте развёртывания.

## 7. Диагностика

- Панель не стартует / не может достучаться до Postgres — `docker compose
  logs panel`, проверить `DATABASE_URL` и что сеть `postgres-net` в
  `docker-compose.yml` совпадает с реальной сетью контейнера Postgres.
- Панель не может выполнить команды на хосте — проверить SSH руками с той
  же машины, где крутится Docker:
  ```
  ssh -i ./secrets/id_ed25519 protean@<SSH_HOST> 'sudo wg show'
  ```
  Если `SSH_HOST=host.docker.internal` не резолвится — проверить, что
  Docker версии ≥20.10 и что `extra_hosts: host.docker.internal:host-gateway`
  есть в `docker-compose.yml` (уже есть по умолчанию в этом репозитории).
- `sudo: a password is required` при вызове `wg`/`awg` из-под `protean` —
  значит `/etc/sudoers.d/protean` не установился (скрипт печатает явную
  ошибку, если `visudo -cf` не прошёл) или путь к бинарю в правиле не
  совпадает с реальным (`command -v wg` может отличаться, если ставили не
  через сам скрипт). Проверить: `sudo -l -U protean`.
- Образ панели — `distroless/static`, в нём нет ни шелла, ни `wg`, ни
  `psql` — `docker compose exec panel sh` не сработает. Для отладки —
  только логи (`docker compose logs -f panel`) и SSH до хоста напрямую,
  как в пункте выше.
- Интерфейс "DOWN" на дашборде сразу после установки — проверить
  `systemctl status wg-quick@wg0` (или `awg-quick@awg0`) на хосте и
  `journalctl -u wg-quick@wg0`.

## 8. Установка VPN из панели (страница Install)

Панель умеет ставить VPN на хост сама: страница **Install** показывает
определённую ОС/пакетный менеджер и статус каждого провайдера, кнопка
«Install» ставит выбранный.

Как это безопасно: панель по SSH вызывает **единственный** root-owned скрипт
`/usr/local/lib/protean/protean-installer.sh` (положен `setup-host.sh`,
0755 root:root, панель менять его не может). sudoers даёт NOPASSWD **только
на этот путь**; допустимые действия — строгий enum (`detect`,
`install wireguard|amneziawg|openvpn|ikev2`), аргументы валидируются и в
скрипте, и в Go-обёртке. Произвольные команды панель выполнить не может.

Пер-дистрибутивные особенности, которые скрипт учитывает:
- **apt** (Debian/Ubuntu/Mint/Pop/Kali/…): WireGuard — пакет `wireguard`;
  AmneziaWG — PPA `ppa:amnezia/ppa` (Ubuntu) или DEB822-репо (Debian).
- **dnf** (Fedora/RHEL/Rocky/Alma/Oracle/Amazon 2023/…): WireGuard —
  `wireguard-tools`; AmneziaWG — COPR `amneziavpn/amneziawg`; учёт SELinux.
- **pacman** (Arch/Manjaro/EndeavourOS/Garuda/…): AmneziaWG — через AUR
  (нужен установленный `yay`/`paru`, иначе понятный отказ).
- **zypper** (openSUSE): WireGuard — `wireguard-tools`; AmneziaWG пакета нет.
- Не-systemd — `detect` возвращает `supported:false`, установка не даётся.

После установки нового интерфейса не забудь: создать/настроить его
(адрес/порт — через сам wg-quick или руками), включить форвардинг на
странице Mesh, открыть порт в файрволе.

## 9. Что дальше (не реализовано, осознанно)

- Управление (не только установка) OpenVPN/IKEv2 из панели — сейчас только
  заглушки интерфейса `vpn.Provider`, реализация — отдельная задача (другой
  формат конфига, своя PKI).
- Мультисервер (несколько VPS под одной панелью).
- Более узкая модель прав на conf-файлы через sudo (см. пункт 6).
- Форвардинг-правила на чисто-nftables хостах без `iptables-nft` шима.
